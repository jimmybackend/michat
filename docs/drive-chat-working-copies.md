# ArcadeCloud files as chat attachments

Selecting **Seleccionar y analizar** now prepares an attachment for the active conversation. If no conversation exists, the browser creates one. It creates a private server-side copy under `Data/Chat/Uploads/<owner>/<UTC year>/<month>/<day>/<session>/`, using the original's verified revision and a unique storage key. `FileS3.Nombre` preserves the display name; `Ruta`, `Encriptado`, `Tamano`, `Found`, `AccessType` and `Metadatos` use the existing schema. `Metadatos.drive_source` identifies the original owner, FileS3 ID, key, ETag, copy ETag and original sibling JSON key. No schema migration is needed.

The original bytes and metadata are preserved. Repeated selection of the same revision/conversation reuses its working copy and focuses it for subsequent questions. Another conversation gets a separate copy. The active conversation, CSRF, owner and live original permissions are checked; making the original secure/deleted invalidates access to the copy and its cached evidence. Failed S3 copies do not create successful FileS3 records. An interrupted operation after creating the S3 object but before committing metadata can leave an unlinked private working object; automated deletion is outside this change.

The file browser returns to chat after attachment preparation and sends the initial file question through the normal message pipeline when the composer is empty. It preserves existing drafts and never auto-sends their contents. The search modal no longer displays the semantic summary as the result of working with a file. Preparation generates/reuses literal chunks without a fresh semantic summary call; image descriptions still require the configured vision service. OCR pending/error states remain explicit. Attachment refresh uses AJAX without reloading the active conversation.

The uploaded example JSON confirmed that extraction had succeeded with four PHP chunks while the chat claimed no file was indexed. Evidence could disappear through configurable attachment/main templates, optional ranking, or code grounding that insisted on project-only file tools. Explicit file requests now retain their evidence; a final prompt guard includes actual authorized chunks/citations even when templates omit placeholders, in both legacy and Task chat paths. Named/active attached-code questions use attachment grounding instead of requiring a project or searching project-only tools. Relative follow-ups such as “qué errores tiene” use the selected working attachment. Global attachment feature restrictions remain respected.

The working copy indexes with its own FileS3 ID and ETag. Compatible verified cached chunks from the original JSON are rebound to that identity without another original download/model call. The private JSON remains at `<original-key>.michat-u<owner>.analysis.v1.json`; it contains the original's cached analysis plus chat questions/answers, session/message IDs and working-copy IDs/keys. Writes for copies of the same original share the original's lock and retain conditional S3 revision checks. A changed original/copy revision cannot silently mix histories; a failed auxiliary JSON write is reported while the chat keeps the messages. This is snapshot analysis, not permission to overwrite originals or automatically apply proposed code edits.

Catalog search remains metadata-only and now searches `Nombre`, `Encriptado`, `Ruta`, `Metadatos`, dates and extensions from either name/key. The owner can expand the real key and metadata in the search results. Internal working copies are excluded from catalog results to avoid duplicate originals. Password hashes are not exposed. Sharing grants are not expanded; current integration supports owned accessible originals.

Validation: `drive_chat_working_copy_mysql_test.php` runs 25 checks against real temporary MariaDB tables and S3 doubles. It covers copy paths/provenance, idempotency, literal cache reuse with distinct copy ETags, actual ContextBuilder/ranker results, custom prompt templates missing placeholders, follow-up grounding, Q&A in the original JSON, cross-user/session isolation, revoked original access, catalog deduplication and copy failures. The JavaScript VM test checks auto-created/existing conversations, attachment POST, chat handoff, stale search isolation and draft preservation. Existing document, HTTP delivery, migration and PHP/JavaScript regressions are also run. Live EC2/S3/Bedrock behavior still needs verification after deploying the merged commit.

## AWS SDK response compatibility

`HeadObject` returns `Aws\Result` in production, an `ArrayAccess` object rather than a PHP array. The original strict array parameters caused a `TypeError` before `GetObject` ran, wrapped as “No se pudo descargar la revisión original desde S3.” Download, document dispatch and PDF/OCR now accept both arrays and `ArrayAccess`, preserving size limits, ETag checks and version-pinned OCR. This defect was reproduced with the actual SDK Result implementation before the fix. Integration fixtures now return objects; CI requires the installed SDK Result instead of silently falling back to arrays. Dedicated checks cover streamed and SaveAs downloads, PHP extraction without execution, and OCR version metadata. A failed attachment preparation also must not auto-send a question or hide its error.

After deployment, retry indexing the existing failed attachment; its presence in the file list only confirms metadata, not extracted content. Verify nonzero chunks and a response citing the source before treating it as ready. No migration or AWS policy change is required for this type fix.
